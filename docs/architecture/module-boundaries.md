## 2. Domain Boundary Rules (non-negotiable)

### Credits must never depend on Payments

`Credits` exposes operations like `reserveCredits()`, `consumeCredits()`, `refundCredits()`, `adjustCredits()` that operate purely on user ID + amount + reason + idempotency key. It has **zero knowledge** of M-Pesa, eMola, or any provider. Per `prompts/12-mpesa-integration.md` §23 ("Provider Independence"): _"The credit system must not know whether payment came from M-Pesa, eMola, Card, Bank. Only the payment subsystem knows the provider."_

### Payments must depend on a provider abstraction, not on M-Pesa directly

`Payments` (not yet implemented) will sit behind the `BillingProvider` interface that Phase 5 already delivered — see the Billing row above. `MpesaBillingProvider` is registered behind it today as a placeholder (every method throws `NotImplementedException`, zero external calls); a real implementation replaces its body without changing the interface or any calling code (Dependency Inversion, per `prompts/00-rules.md` "Architecture Principles"). Once implemented, `Payments` will be the **only** module that calls `Credits` to grant credits, and only after backend-verified confirmation — never from a webhook payload alone without verification, never twice for the same provider transaction (idempotent by provider reference).

### AI must never bypass Credits

Every credit-consuming AI operation flows: `AI service` → checks/reserves cost via `Credits` → calls OpenAI → commits or releases the reservation based on outcome. `AI` never mutates wallet/ledger state directly; it only calls `Credits`' public interface. Concretely, this means wrapping the OpenAI call in `CreditService.spendAndExecute()` (see the Credits row above) rather than calling `spend()` and `refund()`/`reverse()` separately. `AI Request Tracking` (Phase 5) is the metadata side-channel for this flow — it records provider/model/token/cost data via `AiRequestTrackingService` but never itself decides whether to spend or refund credits.

### No AI feature may bypass AI Orchestration

As of Phase 6, "AI service" in the rule above is concretely `AiOrchestrationService` — no feature (Resume Optimization, Cover Letter, Interview, Career Advisor, LinkedIn, ATS AI, Template Recommendation, or any future one) is permitted to call `CreditService`, `AiRequestTrackingService`, or a provider SDK directly; every one of those calls happens exclusively inside `AiOrchestrationService.execute()`'s pipeline. A feature module's only touchpoint with AI is registering a `PromptBuilder` into `PromptRegistry` and calling `execute()`. Adding a real provider (OpenAI, Anthropic, Gemini) means adding a class to `ProviderRegistry`, never adding a second orchestration path. **Resume Optimization (Phase 7), Cover Letter (Phase 8), Interview (Phase 9), Career Advisor (FASE 18), LinkedIn (FASE 19), ATS AI (FASE 20), and Template Recommendation (FASE 21) all prove this in practice**: none of `ResumeOptimizationService`, `CoverLetterService`, `InterviewService`, `CareerAdvisorService`, `LinkedInService`, `AtsAiService`, or `TemplateRecommendationService` has a constructor dependency on `CreditService`, `WalletService`, `RefundService`, `ProviderRegistry`, or any `AIProvider` — only on `AiOrchestrationService`, structurally enforcing the rule rather than merely documenting it. Interview is also the first feature registering **two** `PromptBuilder`s (question generation and answer evaluation are distinct `AIFeature` keys, `INTERVIEW_QUESTIONS`/`INTERVIEW_EVALUATION`) — proving the rule holds even when a feature needs more than one AI operation. Career Advisor is the first feature whose context is drawn from **8** other modules, all optional; LinkedIn deliberately narrows that same pattern to **4** modules, matching its own briefed scope rather than reusing Career Advisor's broader one. ATS AI is the first feature that never gathers fresh context at all — it reads an already-computed `AtsReport` and recalculates nothing, the clearest structural proof yet that "AI interprets, the deterministic engine computes" holds even under this same shared pipeline. Template Recommendation adds a distinct proof of its own: the `responseValidator` closure not only re-parses the AI's JSON shape (the pattern every feature already follows) but also cross-checks each returned `templateId` against the real `ResumeTemplate` catalog fetched moments earlier, throwing — and triggering the same automatic refund — the moment the AI names a template that does not exist, so an unusable recommendation is never persisted and never silently charged. See [ai-orchestration.md](ai-orchestration.md) §1, §11, [resume-optimization.md](resume-optimization.md) §11–12, [cover-letter-engine.md](cover-letter-engine.md) §10, [interview-engine.md](interview-engine.md) §12, [career-advisor-engine.md](career-advisor-engine.md) §1, [linkedin-engine.md](linkedin-engine.md) §1, [ats-ai-engine.md](ats-ai-engine.md) §1-2, and [template-recommendation-engine.md](template-recommendation-engine.md) §1-2.

### Export Engine is not an AI feature — it charges Credits directly, never through AI Orchestration

Unlike Resume Optimization/Cover Letter/Interview, `ExportService` has a direct constructor dependency on `CreditService` and calls `spendAndExecute()` itself — this is intentional, not a violation of "No AI feature may bypass AI Orchestration" above, because generating a PDF/DOCX involves no prompt, no provider, and no AI-generated content at all; the exported content is exactly what is already stored. `CreditsModule` exporting `CreditService` was always meant to support exactly this kind of direct, non-AI reuse (see its own module doc comment). Export Engine must never route through `AiOrchestrationService`/`PromptRegistry`, and no future non-AI paid feature should either — that pipeline exists specifically for actual provider calls. See [export-engine.md](export-engine.md) §7.

### The Smart Application Pipeline is an orchestration layer — it never re-implements the logic of the features it wires together

`ApplicationPipelineService` has constructor dependencies on `ResumeVariantService`, `JobTargetService`, `AtsAnalysisService`, `ResumeOptimizationService`, `CoverLetterService`, `InterviewService`, `ExportService`, `ApplicationService` — and nothing else. It never has a dependency on `CreditService` or `AiOrchestrationService`, for the same reason Export Engine doesn't call `AiOrchestrationService` directly: it makes no AI call and charges no credits of its own — every step's cost is charged independently by the service that step delegates to. Each step method does exactly three things: verify the session's ownership, call that step's owning service exactly as any other caller would, and record the resulting id on the session row. See [application-pipeline.md](application-pipeline.md) §3.

### Users is the root aggregate, nothing depends "upward" into feature modules

`Users` has no knowledge of CVs, Credits, Payments, etc. Profiles/CVs/Credits/Payments all reference `userId` but the dependency arrow points one way (feature modules → Users), never back.

### CVs never touches billing directly

`CVs` triggers paid operations (improve, translate, analyse) by calling `AI`, which in turn calls `Credits`. `CVs` never calls `Credits` directly and never hardcodes credit costs (costs are configuration owned by `Credits`/Admin, per `prompts/11-credit-system.md` §4).

### Master Resume is the source of truth; CVs never duplicate its data

Per `prompts/09-product-vision.md`'s "one master resume, CVs are filtered versions" requirement:
`CVs` (when implemented) reads from `Master Resume` to generate a snapshot — it never accepts
independently-entered experience/education/skills from the user. Professional-data mutations only
ever happen through `Profile`/`Master Resume`'s endpoints. See
[master-resume-data-model.md](master-resume-data-model.md) §5.

### Job Target does not implement AI — it only stabilizes the future interface

`JobTargetAnalysisService`'s four methods (`extractKeywords`, `calculateATS`, `generateResumeSuggestions`, `generateCoverLetter`) exist solely so a future `AI` module has a fixed contract to implement against; every method throws `NotImplementedException` in Phase 2B and no controller route calls them. When `AI` is implemented, it depends on `JobTargetAnalysisService`'s interface (or replaces it), never the reverse — `Job Target` never calls out to OpenAI or any AI module itself.

### Application never mutates Job Target or Master Resume data

`Application` only records tracking metadata (status, dates, notes) about an existing Job Target — it never writes to `job_targets` or any Master Resume table. Creating an Application verifies the referenced Job Target belongs to the same user (via `JobTargetService.assertOwnedJobTarget()`) but does not modify it. The same applies to `resumeVariantId` (verified via `ResumeVariantService.assertOwnedVariant()`).

### Resume Variant reads from Master Resume once, then never again

`ResumeVariant.create()` reads the Master Resume and its 11 sections exactly once — at creation (or, for `duplicate()`, reads only the source Variant, never the Master Resume) — and copies the result into its own `content` column. After that read, `ResumeVariant` holds no live reference back to `MasterResume`/`WorkExperience`/etc.: it is a value, not a view. `MasterResumeService`/`ResumeSectionsService` have no knowledge that Variants exist and never call into `ResumeVariantModule` — the dependency arrow points only one way (Resume Variant → Master Resume), matching the "Master Resume is the source of truth" rule above.

### ATS is deterministic and reads, never writes, its two inputs

`AtsAnalysisService` fetches a Resume Variant and its linked Job Target through their own ownership-checked service methods (`ResumeVariantService.getOne()`, `JobTargetService.getOne()`) — it never mutates either. Every score comes from pure functions in `ats-scoring.util.ts` (no I/O, no randomness, no AI/OpenAI call anywhere in the module) — the same Variant + Job Target pairing always produces the same scores. This keeps ATS analogous to a read-only report generator, not a feature that could accidentally corrupt the data it's analyzing.

### Resume Version History is a leaf — it never depends back on Resume Variant

`ResumeVariantModule` imports `ResumeVersionModule` (for `ResumeVersionRepository`, to write a version row on every content-changing action) — a one-directional dependency. `ResumeVersionModule` has zero import of `ResumeVariantModule`: its own read methods (`ResumeVersionRepository.findAllByVariantId()`, etc.) enforce ownership directly via a relation-filtered Prisma query (`resumeVariant: { userId, deletedAt: null }`) instead of calling back into `ResumeVariantService`. If it needed to call back, the two modules would form a circular dependency — this codebase resolves that class of problem by always making one side a leaf, never by allowing the cycle. See [resume-version-history.md](resume-version-history.md) §2.

### Template Engine is a leaf — it never depends back on Resume Variant or Cover Letter, and never renders anything

Same pattern as Resume Version History (§ above): `ResumeVariantModule`/`CoverLetterModule` each import `TemplateEngineModule` (for `ResumeTemplateRepository`/`CoverLetterTemplateRepository`, to validate a `templateId` before saving it); `TemplateEngineModule` has zero import of either. Additionally, `TemplateEngineService` never produces HTML/CSS/rendered output of any kind — that logic lives entirely in the frontend (`apps/web/lib/template-engine/`, `apps/web/components/template-engine/`), so a future PDF/DOCX export or marketplace admin tool can reuse the same catalog without inheriting a backend rendering dependency. See [template-engine.md](template-engine.md) §2–3.

### Admin is a privileged read/orchestration layer, not a bypass

Admin actions that touch Credits (manual adjustment) or Payments (refund approval) must still go through the same audited, ledger-writing service methods as normal flows — never direct DB writes. Every admin action affecting credits/payments/users/permissions/AI config produces an audit log entry (`prompts/10-business-rules.md` §17).
