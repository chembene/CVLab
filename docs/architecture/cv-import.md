# CVLab AI — CV Import Engine

Status: **backend implemented, Phase 10.5** (2026-08-04); **frontend integrated, idempotency-hardened, Phase — CV Import User Flow Integration** (2026-08-11); **parser robustness hardened against real user CVs, three rounds, including a root-cause fix for 2-column PDF layouts** (2026-08-11/12, §7a/§7b/§7c); **Phase 12 — canonical model completed, explicit merge/replace strategy, deterministic conflict preview** (2026-08-12, §13); **audit-driven reliability pass — header false-positive fix, DOCX column-awareness, entity-name normalization, per-entry Existente-vs-Importado merge resolution** (2026-08-12, §14); **StructuredResumeDraft (per-entry confidence/source/warnings) + Review UI checklist/manual-add** (2026-08-12, §15). Lets a user upload an existing CV (PDF/DOCX) and have it deterministically parsed into their Master Resume, with a mandatory review step before anything is persisted. This document was referenced from `apps/api/src/cv-import/cv-import.service.ts`'s doc comment since the backend phase shipped but was never actually written until this phase's documentation audit caught the gap.

## 1. Why this module exists

Per the brief: eliminate manual data entry wherever the platform can extract it instead. Before this feature, the only way to populate a Master Resume was typing every field by hand. CV Import turns an existing PDF/DOCX résumé into a pre-filled, user-reviewable draft.

## 2. The flow

```
Upload (PDF/DOCX)
        │  POST /cv-import/upload
        ▼
Text extraction (pdfjs-dist for PDF, mammoth-style for DOCX)
        │
        ▼
Deterministic structured extraction — CVParser (regex + PT/EN section-header heuristics, NO AI)
        │
        ▼
CvImport row, status EXTRACTED — a staging preview, nothing written to Profile/MasterResume yet
        │
        ▼
Review (frontend) — user edits/removes any field or entry
        │  POST /cv-import/:id/confirm
        ▼
Profile + Master Resume + section rows created/updated
        │
        ▼
CvImport row, status CONFIRMED
```

**"Never automatically save imported data"** is enforced structurally, not by convention: `upload()` only ever writes a `CvImport` row (`extractedData`/`fieldConfidence` are the preview's data source); every other table (`profiles`, `master_resumes`, the 6 confirmable section tables) is untouched until `confirm()` runs, and `confirm()` only runs on an explicit user action.

## 3. Why extraction is deterministic, not AI (Step 17 of this phase's brief, restated)

`CVParser` (`apps/api/src/cv-import/cv-parser.ts`) is pure regex/heuristic matching over the extracted text — no OpenAI call, no `AiOrchestrationService` involvement anywhere in this module. This is a deliberate, non-negotiable architecture decision, not a missing feature: routing a user's real uploaded document through a generative model risks inventing or altering companies, dates, degrees, or skills that aren't actually in the file — a direct violation of CLAUDE.md's "AI must never invent qualifications" rule. A future AI _validation_ pass (flagging possible issues) could sit downstream of this module without ever becoming the source of the factual data itself; AI-driven resume _improvement_ already exists as a separate, clearly-labeled feature (see [resume-optimization.md](resume-optimization.md)) that only ever rewords existing, user-confirmed content.

## 4. Database

`CvImport` model (migration from Phase 10.5's schema pass): `id`, `userId`, `fileName`, `fileType` (`PDF`/`DOCX`), `fileSizeBytes`, `status` (`PENDING`/`EXTRACTED`/`CONFIRMED`/`DISCARDED`/`FAILED`), `rawTextExcerpt` (bounded to 2000 chars — PII-minimization, not a second full copy of the CV), `extractedData`/`fieldConfidence` (JSON), `creditsUsed` (always `0` — this module never charges; the column's original comment already anticipated a future paid "AI Extraction" step, see §13's AI-normalization deferral), `masterResumeId` (set once `confirm()` succeeds), `errorMessage`. Soft-deleted via `deletedAt` (`remove()`); `discard()` is a separate, non-destructive status transition that keeps the row for audit. No new columns added in Phase 12 — the canonical-model extension (§13) lives entirely in `extractedData`'s JSON shape, not the schema. Full row shape in [database-overview.md](database-overview.md).

## 6. Confidence

`CVParser.parse()` computes a confidence score (0–1) **only for the 6 `personalData.*` fields it regex-matches** — email, phone, linkedin, github, website, fullName. Array sections (work experience, education, skills, languages, certificates, projects) and the summary are **never scored**: they come from deterministic section-header parsing over a variable-length block of text, not a single matched value, so there is no meaningful per-field confidence to compute for them. `CvFieldConfidence` (`Record<string, number>`) — a missing key means "not scored," not "scored zero."

The frontend review screen (§8) reflects this honestly: a confidence badge renders only for a key that's actually present in the map (`lib/cv-import/confidence.ts`'s `hasConfidenceScore()`). It never fabricates a "low confidence" badge for an array entry just because no score exists — conflating "unscored" with "uncertain" would mislead the user during review.

## 7. Two idempotency/resilience fixes (this phase's audit)

The backend module was fully built and tested in Phase 10.5, but only for a user's _first_ import. This phase's Step 11 idempotency audit found and fixed two real gaps in `CvImportService.confirm()`, both additive (no endpoint signature or route changed):

1. **Re-importing against an existing Master Resume used to 409.** `confirm()` unconditionally called `MasterResumeService.createForUser()`, which throws `ConflictException` if a Master Resume already exists (created manually, or by an earlier confirmed import). Fixed by checking `getForUser()` first and branching to `updateForUser()` when one already exists — "Master Resume is populated **or updated**," not only ever created once per account. Retrying the _same_ already-`CONFIRMED` import is still correctly rejected — that guard (`cvImport.status !== 'EXTRACTED'`) runs before this branch is ever reached, so the pre-existing e2e test asserting that rejection needed no changes.
2. **A single duplicate entry used to abort the entire confirm.** `ResumeSectionsService.create()` throws `ConflictException` on a case-insensitive duplicate (enforced only for skills/certificates/educations — see [master-resume-data-model.md](master-resume-data-model.md) §3). With no transaction wrapping `confirm()`'s section-creation loop, one duplicate skill on a re-import would throw partway through, leaving some sections created, others not, and the `CvImport` row stuck at `EXTRACTED` forever. Fixed by wrapping each `sectionsService.create()` call (`CvImportService.createSectionOrSkip()`) to catch a `ConflictException` and push a `"<label> (already exists on this resume)"` entry into `skippedEntries` — the exact same graceful-skip pattern already used for entries missing a required field, just extended to cover this second failure mode. A non-duplicate error still propagates and fails the request; only the specific "this exact entry already exists" case is treated as a skip.

Both are covered by new unit tests (`cv-import.service.spec.ts`) and new e2e tests (`test/cv-import.e2e-spec.ts`) — see §11.

3. **The re-import fix above solved the backend 409, but real-user testing found the UX itself was still wrong**: confirming silently merged the new CV into the existing Master Resume with no warning. Fixed at the frontend, not the backend — `app/dashboard/import-cv/page.tsx` now branches to an `existing-resume-choice` screen (gated on `useMasterResume()`'s resolved data, captured right after upload) _before_ the review screen ever renders. Phase 12 (§13) replaced this screen's original "Atualizar" / "Rever dados primeiro" pair with the brief's exact explicit choice: "Substituir Currículo Principal" / "Mesclar com Currículo Principal" / "Cancelar". §8 and §11 cover the added state and tests.

## 7a. Parser robustness hardened against real user CVs (2026-08-11/12)

A real user test surfaced "CV Import only extracts name and contact" — every array section (experience, education, skills, etc.) came back empty despite the CV containing that content, plus a Master Resume field-swap bug (an experience entry's `position` and `company` both getting the same wrong text). Diagnosed by tracing the full pipeline (file → extraction → raw text → section detection → `CVParser` → normalization → review DTO) against the real uploaded CV's stored `rawTextExcerpt`, rather than guessing and adding regex blind. Root causes found, in the order they were hit:

1. **An unrecognized section header silently dropped its entire content.** `splitIntoSections()` only ever appended a line to the "current known" section; a header the keyword dictionary didn't recognize left every line under it unclaimed and unrecoverable. Fixed by tracking `unclaimed` lines separately and recovering date-anchored chunks from them (`parseFallbackDatedEntries()`, at reduced confidence) when `workExperiences`/`educations` come back empty — but never fabricating an entry from unclaimed text with no date range in it.
2. **Wide letter-spacing in stylized PDF headers** (`"E X P E R I Ê N C I A   P R O F I S S I O N A L"` — common in Canva-style templates) defeated every keyword match outright. Fixed via `collapseLetterSpacing()`, a preprocessing pass that collapses a line back to normal spacing only when most of its tokens are single characters (so normal short words/acronyms are never touched).
3. **A short-bullet-per-achievement CV format merged multiple distinct jobs into one entry** — `chunkEntries()`'s only trigger for "this line starts a new entry" was "arrives right after a long description line," which never fires when every bullet is short. Fixed by adding a second signal: the current chunk already contains a date range (i.e. we're past its own opening line) and the incoming line doesn't read like a sentence (no trailing `.`/`!`/`?`).
4. **Two real, distinct "date + company" layouts put the company name into the wrong field or lost it entirely.** Some CVs put the date and title/company on one line with the real title on the next; others split the date and company across two separate lines entirely, with a third line for the title. The original one-line-only split logic couldn't handle either. Fixed with a shared `splitEntryTitleAndSubtitle()` used by both `parseExperience()`/`parseEducation()`, plus (real-CV-confirmed) a dedicated "date-led entry line" signal in `chunkEntries()` so a line like `"2018 - 2019 Beta Consultoria, Lda"` — which can never trigger the existing "starts with a capital letter" signal — is still recognized as opening a new entry instead of being silently absorbed as the _previous_ entry's trailing description.
5. **A PDF-wrapped bullet's first physical line looked exactly like a second title line** (short, capitalized, no trailing punctuation) once (4) started reliably producing chunks that already contain a date. Disambiguated by checking whether the _next_ line continues the sentence in lowercase — a genuine second title line never has a lowercase continuation after it; a mid-sentence PDF line-wrap always does.
6. **A comma inside a company's legal suffix** (", Lda" / ", SA" — routine in Mozambican company names) was being caught by the title/company separator regex, tearing "Beta Consultoria, Lda" into two. Fixed by removing `,` from the separator character class.

**Verification discipline**: every fix above was checked against the real user's actual `cv_imports.rawTextExcerpt` (pulled directly via a temporary, non-committed Prisma script, never pasted into chat — deleted once verification was complete) before being converted into an anonymized unit test, not just against synthetic fixtures. `personalData.city`/`address`/`github`/`website` coming back empty for that same user's CV was separately confirmed to be **correct behavior, not a bug** — the source document genuinely never mentions a city/address/GitHub/website, and the parser never fabricates a value for a field the text doesn't contain.

**Known limitation carried forward, not fixed this pass**: 2-column/sidebar PDF layouts (e.g. Skills/Languages in a side column next to Education/Experience in the main column) can have their content extracted out of visual reading order, since `pdfjs-dist` returns text in content-stream order, not layout order — this can misattribute a sidebar section's lines to whichever main-column header precedes it in the stream. Fixing this properly needs position-aware text extraction (grouping by X/Y coordinates before linearizing), which is a materially larger change than a parsing-heuristic fix and was out of scope for this debugging pass; the mandatory review screen (§1, §8) is the user's safeguard against this specific failure mode today.

## 7b. Second round: a different real CV surfaced two more extraction-order artifacts (2026-08-12)

A second real-user test (a different CV, English, "MEL Coordinator" role) hit two more failure modes — both, again, diagnosed against the actual uploaded document's real `rawTextExcerpt`, not guessed:

1. **A letter-spaced section header glued directly onto its own body paragraph, on the same physical extracted line, with no line break in between** — e.g. `"P R O F I L E Monitoring, Evaluation, and Learning (MEL) Professional with over 7 years..."`. `headerAt()`'s length gate (a header line is never allowed to be paragraph-length) rejected the whole line outright, so `PROFILE` was never recognized as a header AND the entire paragraph got misattributed as body content of whatever section preceded it — in this document, that was `experience`, turning the summary paragraph into a bogus first "job" whose garbled letter-spaced text ended up as its position. Fixed with `splitGluedLetterSpacedHeader()`: detects a run of 3+ single-character tokens at the very start of a line (the unambiguous letter-spacing signature — no ordinary word is ever tokenized letter-by-letter) whose collapsed form exactly matches one of the known header keywords, and splits the line into two — the header, and the body text as its own line. Deliberately narrow (exact keyword match on the collapsed prefix only) to avoid misfiring on an ordinary sentence that happens to start with a header-like word.
2. **Once (1) let `PROFILE` become its own recognized `summary` section, it started swallowing the real job entries that followed it**, since nothing but a header can normally end a section and none appeared between the profile paragraph and the first "date + company" line — a further symptom of this same document's 2-column extraction-order scrambling (§7a's disclosed limitation): "Work Experience" as a header appeared _before_ "Profile" in the linearized stream, not after. Fixed by treating a date-led line with real trailing text (the same signal already used for §7a point 4's chunk-boundary detection, now shared via `isDateLedLineWithTrailingText()`) as strong enough evidence on its own to implicitly close a `summary` section and reopen `experience` — scoped deliberately to `summary` only, the one section this was actually confirmed to happen on.
3. **A PDF-wrapped bullet's first physical line was still occasionally mistaken for a new entry title** even after §7a point 5's lowercase-continuation check, specifically when the wrap happened to break right before _another_ capitalized acronym/proper noun (`"...funded by USAID, ECHO,"` / `"SIDA, FCDO, and others..."`) rather than a lowercase word. Fixed with an independent, more general signal: a candidate title line ending in a bare trailing comma is essentially never a genuine entry title (titles are short noun phrases; a comma only ever trails when a sentence or list got cut off mid-flow by the wrap) — added to both `chunkEntries()`'s title-detection and `splitEntryTitleAndSubtitle()`'s second-title-line check.

The Contact/Skills/Languages sidebar content in this same CV is still misattributed (landing entirely inside `languages`, since `SKILLS` and `LANGUAGES` headers appear back-to-back with no content in between, and the section that "wins" is whichever recognized header came last) — this is the §7a-disclosed 2-column-layout limitation manifesting again, not a new bug, and was left unfixed for the same reason: it needs position-aware extraction, not another heuristic.

## 7c. Root-cause fix: position-aware PDF text extraction (2026-08-12)

A third real-user test on the same CV surfaced the same limitation again, more severely — a second work-experience entry was pulled apart and misattributed into `educations` (its own dated chunk merged with an unrelated education blurb, then classified as education because that blurb's line happened to contain "Bachelor"/"University"). At this point the underlying cause — §7a/§7b's disclosed "`pdfjs-dist` returns text in content-stream order, not visual layout order" — had produced three separate categories of symptom (sections misattributed, entries merged across unrelated blocks, Education-vs-Experience misclassified) from the _same_ root cause. Presented to the user as an explicit choice between another point patch (fast, but this session's own track record shows each one reveals a new adjacent case) versus fixing the actual root cause; the user chose the latter.

**What changed**: `extractPdfText()` no longer just concatenates pdf.js's text items in raw stream order. It now:

1. Groups items into lines exactly as before (same per-line text-joining rule, honoring pdf.js's own `hasEOL`), but additionally captures each line's starting X position and rendered width (`groupTextItemsIntoPositionedLines()`).
2. Runs `reorderLinesForColumns()` per page: splits the page at its horizontal midpoint and checks whether there's a real, unambiguous 2-column signature on _both_ halves — at least 4 lines per side, and at least 60% of each side's lines narrower than 55% of the page width (a genuine column's lines wrap within their own width; a page of ordinary paragraphs is still full-width prose even if a few lines happen to start past the midpoint). Only when both conditions hold does it re-emit the page as two contiguous blocks (all left-side lines in their original vertical order, then all right-side lines in their original vertical order) instead of interleaved-by-draw-order.

This directly targets what actually matters for `splitIntoSections()`: a header must stay adjacent to its own column's body text, never a different column's. It's deliberately **not** an attempt at true bidirectional reading-order reconstruction (which column is visually "first" doesn't affect section-detection correctness) — just a guarantee that the two columns' content never gets interleaved.

**Safety for the overwhelming majority (single-column) case**: the two-sided-evidence requirement means a normal one-column CV — where a bullet list, a right-aligned date, or an indented paragraph might individually start past the page's midpoint — is passed through with its original line order completely unchanged. Covered by dedicated unit tests (§11) exercising `reorderLinesForColumns()` directly with hand-crafted positioned lines (pdf.js's own `hasEOL` heuristic could not be reliably forced into a specific pattern via pdfkit's positioning API for an end-to-end PDF fixture — verified empirically — so the reordering algorithm is tested directly against known-position input, which is the deterministic way to cover it).

**Limitation of this fix, disclosed honestly**: this could not be verified against the user's _exact_ real PDF file — per this module's PII-minimization design (§4), the original uploaded file is never stored, only extracted text/data, so there is no way to re-run extraction against the same binary after the fact. It was verified against (a) all of §7a/§7b's real-CV-derived regression tests (must still pass — they do), and (b) new synthetic 2-column fixtures modeling the exact interleaving pattern this fix targets. Final confirmation requires the user to re-upload the same real CV; a repeat "wrong section" result at that point would mean this specific document's column layout doesn't cleanly match the "split at horizontal midpoint" assumption (e.g., a narrower sidebar than half the page), which would be the next thing to investigate.

**State machine** (`app/dashboard/import-cv/page.tsx`): `idle` (dropzone) → `uploading` (a single `POST /cv-import/upload` request — the four-message cycling label "A carregar / A extrair / A analisar / A preparar" is cosmetic labeling over one real network call, never a fabricated percentage, since the backend can't report granular progress for a synchronous deterministic parse) → `existing-resume-choice` (only when a Master Resume already exists — Phase 12's explicit Substituir/Mesclar/Cancelar, §13d) → `review` (edit/remove, `POST /cv-import/:id/confirm` on submit) → `success` (shows `skippedEntries` if any, plus "Abrir Currículo Principal" / "Voltar ao Dashboard" / "Criar CV para uma vaga") or `error` (retry). **Resume Variants are never auto-created** — "Criar CV para uma vaga" only navigates to the existing Job Targets workflow.

Client-side file validation (MIME/extension/size/empty) in `CvUploadDropzone` is a UX convenience only — the server re-validates unconditionally and is the only trust boundary that matters (§9).

**Discoverability**: a "Importar CV" entry in the sidebar (`lib/nav-items.ts`, under "Currículo"), a dashboard quick action, a prominent onboarding banner on the Dashboard when the user has no Master Resume yet, and both options ("Importar CV" / "Preencher manualmente") on the Master Resume page's empty state.

## 9. Security

- **MIME + extension validated server-side**, never trusting the client (`ALLOWED_MIME_TYPES` in `cv-import.service.ts`) — the frontend's own check is a UX nicety, not the gate.
- **5MB hard ceiling**, enforced twice: Multer's `FileInterceptor` limit (rejects before the handler even runs) and a defense-in-depth re-check inside `upload()`.
- **Never executes uploaded content** — the file buffer is only ever passed to `pdfjs-dist`'s text-extraction API or a DOCX text extractor, never written to disk or run as a script.
- **Ownership enforced on every method** via `assertOwnerOrAdmin()`, same pattern as every controller in this codebase since Phase 2A — a stranger requesting another user's `CvImport` by id gets a 404, not a 403 (existence isn't disclosed).
- **A parse failure never silently creates an empty Master Resume** — `upload()`'s catch block records a `FAILED` `CvImport` row (audit trail) and re-throws a `BadRequestException` with a user-facing message; no Profile/MasterResume/section row is ever touched on a failed extraction.

## 10. Known limitations (disclosed, not fixed this phase)

- ~~No per-array-entry confidence~~ **Resolved by §15** — every entry in all 9 array sections now carries its own `confidence`/`source`/`sourceText`/`warnings` (§15b), not just the 6 `personalData.*` fields. `CvFieldConfidence` (§6) is unchanged and still used for personal info/summary specifically, which stay non-array-shaped.
- **DB-level duplicate rejection at creation time still covers only skills/certificates/educations** — a pre-existing `ResumeSectionsService` behavior this module doesn't control. Phase 12's merge preview (§13c) covers all 9 importable section types, but it's advisory (shown to the user before commit); it doesn't change which section types the database itself refuses a second near-identical row for.
- **Confidence scoring is a hand-tuned point system, not calibrated against real-world accuracy data** (§15b) — the point values (e.g. +0.1 for a present company) encode a reasonable, disclosed ordering (more populated fields → higher confidence), not a statistically validated probability. Treated as a review-priority signal, not a guarantee.
- **No credit cost** — `creditsUsed` is always `0`; this module was never designed to charge, matching "extraction is deterministic, not a paid AI feature." §13f documents the designed-but-unwired AI-normalization path this column already anticipates.
- **No PDF/DOCX preview thumbnail** — the review screen shows extracted _data_, never a rendering of the original document.
- **2-column/sidebar PDF layouts can extract out of visual reading order** for layouts that don't cleanly split at the page's horizontal midpoint (§7c) — a narrower-than-half sidebar, for instance.
- **DOCX 2-column detection (§14b) only recognizes the single-row/2-cell-table layout idiom** — a DOCX using Word's rarer "newspaper columns" print feature (not a table) still extracts in raw paragraph order; this is a materially less common real-world case than the table technique, left unhandled.
- **Merge-preview duplicate detection is exact-normalized-match only, not fuzzy** (§13c, deliberate) — a duplicate phrased even slightly differently across two imports won't be flagged; the review screen remains the final safeguard. §14 adds a per-entry resolution UI (Manter existente/Usar importado/Mesclar) for the duplicates the preview _does_ catch, but does not widen catch itself to fuzzy matches.
- **Original uploaded file is never retained** (§13g) — only the 2000-char text excerpt and structured `extractedData` persist; deferred pending a storage/privacy-policy decision.
- **Entity-name normalization (§14a) is whitespace cleanup only** — it never fixes inconsistent capitalization or reorders words, deliberately (CLAUDE.md/"não alterar o significado original"). `"lgn-contact"` and `"LGN Contact"` are still two different strings to the merge-analyzer's exact-match comparison.

## 13. Phase 12 — Intelligent Resume Import & Normalization (2026-08-12)

Brief: make CV import reliable enough for real-world CVs, formalize a canonical resume model, let a user import even when a Master Resume already exists (with an explicit, non-silent choice — never an automatic overwrite), add deterministic conflict detection before commit, and design (without necessarily wiring live) an AI-normalization contract that can never invent information.

### 13a. Audit-first, then a scoped plan

Per the brief's explicit "do not blindly rewrite" instruction, this phase started with an audit of the existing CV Import, Master Resume, Resume Sections, AI Orchestration, and Credits modules before writing any code. Findings that shaped the plan:

- The canonical resume model the brief asks for (§5 of the brief) **already existed at ~90%** via `ExtractedCvData` + the 11-section-type `SECTION_DEFINITIONS` registry (`resume-sections/section-registry.ts`) and the matching Prisma models — only `awards`, `volunteerExperience`, and `references` were missing from the _import_ layer specifically (they were already fully supported for manual entry via the generic Resume Sections module). `courses`/`publications` exist in the schema too but aren't part of the brief's canonical list, so import-extraction for those two stays out of scope.
- `AIFeature.CV_IMPORT = 'cv_import'` has been reserved in the AI Orchestration feature enum since Phase 10.5, with a comment explicitly anticipating a future "AI Extraction" step for this exact module — but **no `feature_pricing` row for it exists anywhere in the codebase** (no seed data, no configured price). Per the brief's own §20 ("do NOT introduce a new credit price without reviewing current product rules") and CLAUDE.md's financial-integrity rules, this phase does **not** wire a live paid AI call — see 13f.
- `ResumeSectionsService.assertNoDuplicate`'s case-insensitive matching (skills/certificates/educations only) was a ready-made pattern to extend into a full, deterministic, all-section conflict _preview_ — see 13c.
- The sidebar/navigation performance question (brief §22/§23) was already investigated earlier in this same debugging arc and confirmed to be a `next dev`-only on-demand-compilation artifact (cold-route compile ~8.7s vs warm ~16ms, same route, no image/preview involvement) — re-confirmed, not re-investigated from scratch, since nothing about routing/rendering changed in this phase.

### 13b. Canonical model — the 3 missing section types

`ExtractedCvData` (backend `interfaces/extracted-cv-data.interface.ts`, mirrored in `apps/web/lib/api/cv-import.ts`) gained `awards: ExtractedAward[]`, `volunteerExperiences: ExtractedVolunteerExperience[]`, `references: ExtractedReference[]` — each mirroring its Prisma model's shape 1:1, the same "no translation layer" convention the original 6 already followed. `CVParser` gained matching PT/EN section-header keywords (`awards`/`prémios`/`honors & awards`, `volunteer`/`voluntariado`, `references`/`referências`) and three new parse methods:

- `parseAwards()` — same title/issuer/date shape as `parseCertificates()`, plus a dedicated leading-single-year strip (`LEADING_YEAR_RE`) since awards are typically dated with one year, not a range, and `DATE_RANGE_RE` deliberately never matches a bare year (it would misfire on any 4-digit number in body text).
- `parseVolunteerExperiences()` — reuses `splitEntryTitleAndSubtitle()`, identical shape to `parseExperience()` with organization/role instead of company/position.
- `parseReferences()` — per the brief, **only ever populated from an actual "Referências"/"References" block**, never fabricated. Each chunk is anchored on an email or phone number found within it (the one field a reference listing reliably includes); a chunk with neither is dropped rather than guessed at.

`CvImportService.confirm()` and `CvUploadDropzone`'s sibling `CvImportReview.tsx` both gained matching sections (create-or-skip loops on the backend; editable Card sections on the frontend, same pattern as the existing 6).

**Incidental real-world fix found while writing these**: `EMAIL_RE` (`/[\w.+-]+@[\w-]+\.[a-z]{2,}/i`) silently truncated multi-level domains — `"joao@empresa.co.mz"` extracted as `"joao@empresa.co"`, dropping the real TLD. Directly relevant to Mozambique (the platform's initial market, CLAUDE.md), where `.co.mz`-style domains are routine. Widened to `/[\w.+-]+@[\w-]+(?:\.[\w-]+)*\.[a-z]{2,}/i`, covered by a dedicated regression test.

### 13c. Deterministic conflict preview — the Merge Engine (brief §14)

`cv-import-merge-analyzer.ts` — a small, pure, independently-testable module (no NestJS DI, no I/O) exporting `analyzeMerge(extractedData, existingSections)`. For every one of the 9 importable section types, each extracted entry is classified `new` or `possible_duplicate` against the user's existing Master Resume sections, via **normalized-string equality only** (case-insensitive, whitespace-collapsed) on the fields that matter for that section type — e.g. company+position for work experience, institution+degree for education, name only for skills. Deliberately **not** a fuzzy/similarity matcher, per the brief's own caution ("do not use an unreliable fuzzy matcher as the sole decision maker") — this trades recall (a duplicate phrased differently won't be caught) for precision (never falsely flags two genuinely different entries as the same).

`CvImportService.previewMerge()` (new, read-only — never mutates anything) loads the user's existing section rows via `ResumeSectionsService.list()` for all 9 types and calls `analyzeMerge()`. Exposed as `GET /cv-import/:id/merge-preview`. When there's no existing Master Resume yet, every entry is trivially `new` (nothing to compare against) and the section-list calls are skipped entirely.

### 13d. Master Resume already exists — explicit strategy, never automatic (brief §13/§35)

`ConfirmCvImportDto` gained `strategy?: 'merge' | 'replace'`, defaulting to `'merge'` when omitted (backward-compatible with every pre-Phase-12 caller and test):

- **`'merge'`** (default): unchanged from §7's existing behavior — every existing section row is kept, new/edited entries are added, an exact duplicate is skipped (not aborted).
- **`'replace'`**: `CvImportService.wipeExistingSections()` soft-deletes every active section row across all 9 importable types via `ResumeSectionsService.remove()` (one row at a time — respects this module's "compose the domain service, never its repository" rule, same as everywhere else in this service) _before_ the new sections are created. Only ever runs when the frontend explicitly sends `strategy: 'replace'`, itself only reachable from an explicit "Substituir Currículo Principal" button click — never a default, never silent.

Both paths emit a `merged`/`replaced` event (in addition to the existing `confirmed` event, so nothing that already filters on `confirmed` breaks) — `ResumeEntityAction` widened accordingly.

**Frontend**: the `existing-resume-choice` screen now shows the brief's exact three actions — "Substituir Currículo Principal" (destructive-styled, confirms immediately with `strategy:'replace'`) / "Mesclar com Currículo Principal" (routes to the normal review screen, `strategy` stays the `'merge'` default) / "Cancelar" — plus the live merge-preview counts ("Encontrámos N possíveis duplicados e M novas entradas") fetched via `useMergePreview()` the moment the choice screen mounts, so the user has real information before choosing, not just a generic warning.

### 13e. Error messages (brief §18)

Upload's generic messages replaced with specific, actionable Portuguese: "Nenhum ficheiro foi enviado...", "Formato de ficheiro não suportado...", "O ficheiro excede o limite de 5MB...". The parse-failure catch block now distinguishes `InvalidPromptError` (CVParser's own "no extractable text" signal — most commonly a scanned/image-only PDF with no text layer) with a specific, actionable message pointing at that cause, from any other unexpected extraction failure, instead of one generic fallback string for both.

### 13f. AI normalization/extraction — designed, deliberately not wired live

The brief's §8 (hybrid extraction pipeline) and §9 (AI extraction contract: value/confidence/sourceText, "never invent, infer, improve, rewrite, or complete missing information") describe a real, valuable enhancement — but wiring a live paid AI call requires a product decision (a price point for `AIFeature.CV_IMPORT`) that isn't this implementation's to make unilaterally, per the brief's own §20 and CLAUDE.md's credit-system rules. This phase therefore:

- Keeps extraction **100% deterministic**, exactly as §3 already established and CLAUDE.md's "AI must never invent qualifications" already mandates as the safe default.
- Documents the contract here so a future phase can wire it in directly: an AI normalization step, if/when priced, would sit **after** deterministic extraction (not replacing it) — `AiOrchestrationService.execute({ feature: AIFeature.CV_IMPORT, ... })`, following the exact same pattern already proven by `ResumeOptimizationService` (§ resume-optimization.md) — a `CvImportPromptBuilder`/`CvImportResponseParser` pair, credit spend via `CreditService.spendAndExecute()` (validate-before-charge, automatic refund on provider failure), and a strict system prompt enforcing per-field `{ value, confidence, sourceText }` output with an explicit "return null for anything not explicitly present" instruction. `CvImport.creditsUsed` already exists in the schema for exactly this, unused (always `0`) until that day.
- Recommends this as the top candidate for the next CV Import phase (see the session's final report) rather than rushing a design that touches pricing without the appropriate review.

### 13g. Original file retention (brief §17) — deferred, not implemented

Retaining the original uploaded PDF/DOCX (beyond the current 2000-char text excerpt) is a genuine storage-architecture and privacy-policy decision — R2 storage cost per user, a retention/deletion policy, and a widening of what's already a deliberately PII-minimized design (§4's `rawTextExcerpt` comment). Not implemented this phase; flagged as a recommended follow-up requiring explicit product sign-off rather than an engineering default.

## 14. Audit-driven reliability pass (2026-08-12)

A fresh full-module audit (backend + frontend + Master Resume + Merge Engine), requested explicitly before any new code — findings presented to the user as a diagnostic report first (§1 of that report: what already worked, mapped against the brief's own layered-architecture request; most of it already existed). The user then prioritized two of the found gaps for this pass: the per-entry "Existente vs Importado" diff (brief's own worked example: `"LGN-Contact — Supervisor"` vs `"LGN Contact — Customer Line Supervisor"`) and general extraction robustness (header synonyms, entity-name normalization), plus DOCX column-awareness.

### 14a. Header synonym expansion + entity-name normalization

`SECTION_HEADERS` gained additional real-world PT/EN synonyms beyond what the brief explicitly listed (which was already ~100% covered) — e.g. `"resumo pessoal"`/`"apresentação"` for summary, `"trajetória profissional"`/`"career history"` for experience, `"percurso académico"` for education, `"áreas de competência"`/`"conhecimentos"` for skills — added conservatively, avoiding anything ambiguous enough to collide with a different section (e.g. a bare `"cursos"` stays out, since it would collide with the separate, not-yet-imported `Course` model).

New `normalizeEntityName()` (exported from `cv-parser.ts`) — collapses doubled internal whitespace and trims a name-like field (company, position, institution, degree, title, issuer, organization, role, person name, language) before `confirm()` persists it. Deliberately does **nothing** else: no case changes, no reordering, no word removal — whitespace cleanup, never a rewrite, per CLAUDE.md/the brief's own "não alterar o significado original."

**Real bug found and fixed while adding these tests, not introduced by them**: `headerAt()`'s short-line substring fallback (`n.length <= 35 && n.includes(kw)`, meant to catch a header wrapped in decoration like `"== Experiência =="`) was misreading ordinary short body content that merely _contained_ a keyword — e.g. the real, common PT job title `"Gestora de Projetos"` (Project Manager) was being read as a new "Projects" section header, silently corrupting the surrounding work-experience entry. Fixed by requiring the line's remainder, once the matched keyword is removed, to contain no letters at all (i.e. only symbols/digits/spaces survive) — this keeps catching genuine decorated headers while no longer misfiring on a title, sentence, or bullet that happens to mention a section-topic word. Covered by a dedicated regression test using the exact "Gestora de Projetos" case.

### 14b. DOCX column-aware extraction

Unlike PDF (§7c), DOCX extraction had **no column awareness at all** — `mammoth.extractRawText()` returns paragraphs in raw internal document order, and a 2-column CV built in Word almost always uses a single-row, 2-cell `Table` as its layout container (the standard technique; true "newspaper column" layout is a print-only Word feature mammoth doesn't represent). Reading that table naively interleaves the two "columns" cell-by-cell, corrupting section detection exactly like the PDF issue §7c already fixed.

`CVParser.extractText()` now calls `mammoth.convertToHtml()` instead (preserves `<table>`/`<tr>`/`<td>` structure) and a new `extractDocxText()` detects the exact layout-container signature — one `<table>`, one `<tr>`, exactly 2 `<td>` cells, each with 3+ paragraphs (mirrors the PDF fix's "strong, unambiguous evidence only" philosophy) — and emits each cell as one contiguous block. Any table that doesn't match this shape (a genuine multi-row data table, or a short 2-cell header/contact bar) falls straight through to normal whole-document paragraph order, unchanged. A small in-house HTML-paragraph extractor (`extractHtmlParagraphs()`) strips tags and decodes the handful of entities mammoth emits (`&amp;`, `&nbsp;`, etc.) — no new dependency added, since mammoth's own HTML output is simple and self-generated, not arbitrary third-party HTML.

**Known limitation, disclosed**: only the table-based column idiom is recognized; a DOCX using Word's actual multi-column section feature (rare in practice) still extracts in raw order.

### 14c. Per-entry "Existente vs Importado" resolution — the Merge Engine's missing half

Phase 12's merge preview (§13c) already classified each extracted entry as `new`/`possible_duplicate` and surfaced an _aggregate_ count ("Encontrámos N possíveis duplicados"). What was missing was the brief's own worked example: a per-entry side-by-side diff with an explicit choice. Built as a strictly additive extension of the existing engine, no new endpoint:

- **`cv-import-merge-analyzer.ts`**: `MergeEntryResult<T>` gained `existingId?: string` and `existing?: T` — for a `possible_duplicate`, the matched existing row's id and its fields, projected into the exact same shape as the extracted entry (a `Date`-typed DB column becomes a plain `"YYYY-MM-DD"` string, matching how the parser itself represents dates), so the frontend can render both sides without a second round-trip. `GET :id/merge-preview`'s response shape is unchanged apart from these two new optional fields.
- **`ExtractedCvData`'s 9 entity interfaces** (backend `extracted-cv-data.interface.ts`, mirrored in frontend `lib/api/cv-import.ts`) each gained `mergeDecision?: 'use_imported' | 'keep_existing' | 'merge'` and `existingSectionId?: string` via a shared `CvMergeResolution` base interface — purely additive, every pre-existing caller/test that never sets them is unaffected.
- **`CvImportService.confirm()`**: a new `createOrResolveSectionEntry()` routes each entry by its resolution:
  - No decision (the default, everything that was true before this pass): unchanged — create-or-skip.
  - `'keep_existing'`: creates nothing; the existing row is left completely untouched. Reported in a new `keptExistingEntries: string[]` result field.
  - `'use_imported'` / `'merge'`: calls `ResumeSectionsService.update()` on the matched `existingSectionId`, but the payload only ever includes fields the imported entry actually has a defined value for — `undefined` keys are filtered out before the call, so Prisma's own partial-update semantics leave every other column exactly as it was. This is deliberately **non-destructive**: an existing field the import didn't capture (e.g. a `location` the new CV never mentions) is never nulled out. Both decisions share this exact mechanism on purpose — "Usar importado" vs "Mesclar" is a UX preference for the user, not a data-destruction distinction; neither is allowed to silently erase real existing content the import simply didn't capture. Reported in a new `updatedEntries: string[]` result field.
  - A stale `existingSectionId` (the row was deleted, or belongs to someone else, between preview and confirm) is caught (`NotFoundException`) and recorded in `skippedEntries`, never aborting the rest of `confirm()`.
- **Frontend `CvImportReview.tsx`**: a new `MergeDecisionBanner` renders above any flagged entry's fields — a one-line "Existente: ... / Importado: ..." summary (per-section summarizer functions, e.g. `"{position} — {company}"` for work experience) plus three buttons (Manter existente / Usar importado / Mesclar) that set the entry's `mergeDecision` in place. The association between a `reviewData` entry and its matched existing row is seeded **once**, right when `useMergePreview()` resolves (`lib/cv-import/merge-seed.ts`'s `seedExistingSectionIds()` — index-correlated at that exact moment, since the preview and the pristine extracted data share the same order/length; from then on the id lives on the entry itself, immune to the user reordering/removing other entries afterward). The success screen now also lists `updatedEntries` (in addition to the existing `skippedEntries`).

Data-model impact: **none** — no migration, this lives entirely in `ExtractedCvData`'s JSON shape and application logic, same as Phase 12's canonical-model extension.

## 15. StructuredResumeDraft + Review UI checklist/manual-add (2026-08-12)

Brief: give every extracted entry (not just the 6 `personalData.*` fields) a `{ value, confidence, source, sourceText, warnings }` shape, and let the review screen show the user a top-level checklist plus per-entry provenance before confirming — without introducing AI anywhere, without breaking the existing merge/replace/mergeDecision/confirm flow.

### 15a. Design decision: metadata baked onto each entity, not a parallel wrapper

The brief's own example is a literal `{ value, confidence, source, sourceText, warnings }` wrapper around each entry. This phase deliberately implements the _same information_ differently: a new `CvDraftMeta` interface (`confidence?`, `source?: 'document' | 'fallback'`, `sourceText?`, `warnings?: string[]`) is mixed into each of the 9 `Extracted*` entity interfaces directly (alongside FASE 7's `CvMergeResolution`), rather than wrapping every entry in a second object. Reasons, in order of weight:

1. **Avoids reintroducing the exact index-alignment fragility FASE 7 already had to solve.** A parallel `entry: T` / `draft: DraftMeta` structure needs to stay correlated with `reviewData`'s array as the user edits/reorders/removes entries in the review screen — precisely the problem `cv-import-merge-analyzer.ts`'s `existingId`/`existing` fields (§14c) were introduced to solve for the merge diff banner, via a one-time index seed. Baking the fields directly onto the entity means the metadata simply _travels with_ the entry through every edit/removal — no seeding step, no desync risk, ever.
2. **Zero schema/API-contract change.** `StructuredResumeDraft` is exported as a named type alias (`= ExtractedCvData`) so the brief's own vocabulary exists in the codebase and is discoverable — but nothing about `confirm()`'s payload shape, `ConfirmCvImportDto`'s validation, or the merge-analyzer's `classify()` functions needed to change. All four are proven safe already: `CvMergeResolution`'s `mergeDecision`/`existingSectionId` fields (FASE 7) went through the exact same "just more optional properties on the entity, `ValidationPipe`'s `forbidNonWhitelisted` doesn't reach inside a plain-object array item without `@ValidateNested()`" reasoning, verified once and reused here without re-deriving it.
3. **No new Prisma migration.** Everything lives inside `extractedData`'s existing JSON column, exactly like Phase 12's canonical-model fields and FASE 7's merge-resolution fields before it.

### 15b. Confidence scoring — real signals only, disclosed per section type

`cv-parser.ts` gained one `score*()` function per section type (`scoreWorkExperience`, `scoreEducation`, `scoreCertificate`, `scoreProject`, `scoreAward`, `scoreVolunteer`, `scoreReference`, `scoreSkill`, `scoreLanguage`) — each a small, deterministic point system based only on which of that entry's OWN fields are actually populated (e.g. work experience: +0.1 for a present company, +0.1 for a present position, +0.1 for a start date, +0.05 for an end date/`currentlyWorking`, +0.05 for a description; a missing field adds a specific warning instead of silently lowering the score). Every document-sourced score is capped at 0.9 (`clampConfidence()`) — even a fully-populated entry is a heuristic read of unstructured text, never treated as certain. `buildSourceText(chunk)` captures the entry's own raw source lines (joined, capped at 240 chars) for the review screen's "Fonte: ..." quote — a genuine substring of the document, never fabricated; skills/languages (single-token entries with no richer chunk) get no `sourceText`, honestly, rather than a redundant echo of the value itself.

**Fallback entries are never allowed a confidence higher than a document-sourced one.** `parseFallbackDatedEntries()` (recovery from unclaimed text with no recognized section header, §7a) now runs every recovered entry through `markAsFallback()`, which overrides `source: 'fallback'`, fixes `confidence` at `0.3` regardless of how complete the entry looks, and prepends an explicit warning — replacing whatever the underlying `scoreWorkExperience()`/`scoreEducation()` call computed for the "as if it were document-sourced" case. This is a deliberate, tested invariant (§15d).

### 15c. Frontend: checklist, per-entry provenance, and "+ Adicionar"

- **`lib/cv-import/section-status.ts`** — a pure `computeSectionStatuses(data, fieldConfidence)` deriving one of `'found' | 'partial' | 'not_found' | 'needs_review'` per section (11 rows: personal info, summary, plus the 9 array sections), from real data only. An empty array is always `'not_found'`, never upgraded to `'found'` just because the key exists. `'needs_review'` fires when any entry carries a warning or came from the fallback path; `'partial'` when confidence is mediocre but nothing is explicitly wrong; `'found'` otherwise. Personal info/summary reuse the pre-existing per-field `CvFieldConfidence` map (§6, unchanged) rather than `CvDraftMeta`, since they were never array-shaped.
- **`components/cv-import/SectionChecklist.tsx`** — renders that as a labeled list (✓/⚠/○ icons + PT status label) in a new "Resumo da importação" card at the very top of `CvImportReview`.
- **`EntryDraftInfo`** (in `CvImportReview.tsx`) — renders a confidence-tier badge (reusing the same high/medium/low bands and icon vocabulary as the pre-existing `ConfidenceBadge`, via a new `getEntryConfidenceTier()` in `lib/cv-import/confidence.ts`), a "Recuperado automaticamente" badge for `source: 'fallback'`, the entry's `warnings`, and the "Fonte: ..." quote — above each entry's editable fields, for all 9 section types (skills/languages, being compact pill/card rows, get an aggregated warnings list above the row instead of a per-pill block, to avoid cluttering the compact layout). Renders nothing at all for an entry with no draft metadata whatsoever — the honest state for a manually-added entry, which never gets fabricated confidence/source values.
- **"+ Adicionar {secção}"** — a button at the bottom of every one of the 9 sections (not just when empty) appends one blank entry to `reviewData` client-side; nothing is written to the Master Resume until "Confirmar e importar". The exact brief wording — "Não encontramos informações nesta secção." / "Pode adicionar manualmente." — replaces the old generic "Nada encontrado no documento." when a section has zero entries, via a new `EmptySectionNotice`.

### 15d. What stayed untouched, on purpose

Per the brief's explicit constraints: no AI call anywhere in this phase (scoring is 100% arithmetic over already-extracted fields); `ExtractedCvData`'s shape, `confirm()`'s section-creation logic, `strategy`/`mergeDecision` handling, and the Merge Engine (§14c) are all byte-for-byte unchanged — verified by re-running every pre-existing test unmodified (all passed without touching a single assertion) before adding new ones; no new Prisma migration; no new credit consumption (`creditsUsed` stays `0`, untouched); Resume Variants are still never auto-created from an import.
